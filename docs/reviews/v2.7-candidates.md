## 1 — Nothing sends a delivery; the dispatcher does not exist

**Severity: high, and it is the third version in which delivery has been "nearly done".**

v2.5 signed. v2.6 emitted, retried and dead-lettered. Neither posts anything: `pending_deliveries()` returns rows and no loop consumes them. §15.3 promises at-least-once delivery and the repository has at-least-once *bookkeeping*.

**Proposed resolution.** A dispatcher that drains `pending_deliveries()` and posts the signed body, with a local receiver in the tests that fails twice and then accepts — which is the only way to prove the retry path end to end. It is thirty lines and it closes the last gap between the promise and the behaviour.

## 2 — Quotas cover submissions and not the things that cost money

**Severity: high.**

§16.1 lists four quotas: concurrent jobs, submissions per minute, stored bytes and render minutes. v2.6 implements the second. The other three are the ones that cost money — a tenant can submit within the limit and still consume a terabyte of storage or a thousand GPU-minutes.

**Proposed resolution.** Render minutes are already derivable: the store knows the resolution and the duration, and §20 prices the minute. A quota on stored bytes needs the asset table, which this reference does not have. Split the finding: implement render minutes, defer stored bytes with a note saying why.

## 3 — Revocation is per-process and per-restart

**Severity: high, and it is the same shape as the defect it replaced.**

`Tokens.revoked` is a set in memory. A revoked token is rejected by the process that revoked it and accepted by every other process, and accepted again by the same process after a restart. That is a revocation list that does not revoke.

**Proposed resolution.** Put the revocation set in the store, consulted per request. The table is three columns and the lookup is on the hot path, which is why it belongs in the same SQLite file the job state already uses.

## 4 — The rate limiter has no shared state across processes

**Severity: medium, and it follows from the same mistake.**

`ratelimit.Buckets` keeps its tokens in a dictionary, so two workers behind a load balancer each allow a full burst. The effective limit is `capacity × workers`, which is not the limit anyone configured.

**Proposed resolution.** Move the bucket into the store as a row per tenant, with the refill computed on read. One `UPDATE … RETURNING` and the limiter becomes correct under concurrency, which is the only condition it exists for.

## 5 — Six of nine signals: the three GPU ones remain unemitted

**Severity: medium.**

The heartbeat landed in v2.6. GPU memory, encoder utilisation and success rate by kind still need a worker with a GPU, and the benchmark workflow has no runner to give it one.

**Proposed resolution.** Nothing to do until a GPU runner exists. The honest state is the one §17 now describes, and the finding stays open rather than being closed with prose.

## 6 — The identity corpus still has no data

**Severity: medium, and unchanged for four versions.**

Procurement. `tests/corpus.py` remains the specification of what to buy.

**Proposed resolution.** Buy it, or drop the feature from the roadmap and say so — which is what v2.4 did with overlays and what this repository has been doing consistently since then.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Findings 3 and 4 are the same mistake twice: state that belongs in a shared store kept in a process-local dictionary. That is v2.6's own contribution to the pattern, and it is the third time a fix has created a copy of the thing it was fixing.
