## 1 — The worker has no scheduler, no concurrency and no retry policy

**Severity: high, and it is the honest limit of v2.2.**

`tests/store.py` gives the worker a claim, a checkpoint and an orphan requeue. It does not give it a retry policy, a backoff, a concurrency limit, a fairness rule across tenants, or a priority. §18 specifies retry by failure class — transient, resource, permanent, budget, awaiting input, poison — and none of that is implemented.

A worker that requeues every orphan unconditionally will, on a job that crashes the process, loop forever. That is the failure the poison class exists to prevent.

**Proposed resolution.** A retry policy keyed to the error code, with an attempt ceiling and a quarantine state, and a test that a job failing identically three times stops being retried. That is four lines of state and one table.

## 2 — The render fixtures have no audio transition

**Severity: medium, verification debt.**

§5.7 gives audio handles a rule — a record boundary converted to samples once, never a rounded half doubled — and the tests assert the arithmetic. No fixture renders an `acrossfade`, so the rule has never met ffmpeg.

The audio bus test mixes two tracks from the start and never overlaps them, which is the easy half.

**Proposed resolution.** An `acrossfade` fixture with a known overlap, a golden hash, and an assertion that the decoded sample count equals `samplesFor(record duration)` within one sample. That is §11.5's acceptance test, which the document already specifies and the repository does not run.

## 3 — The corpus contract has no data and no loader path in CI

**Severity: medium.**

`tests/corpus.py` validates a labelled set and nothing calls it with real data, because there is none. The contract is right and untested against a file.

**Proposed resolution.** A committed *fixture* corpus — synthetic embeddings, clearly labelled as such — so the loader, the validator and the rate computation run end to end in CI. The real corpus is procurement; the pipeline should not be.

## 4 — The perceptual fallback has no golden fingerprint

**Severity: low.**

`renderer.perceptual()` computes a fingerprint and a mean absolute difference, and nothing records what the fingerprint should be. It is exercised only by a self-comparison, which proves it is deterministic and not that it is right.

**Proposed resolution.** Record a fingerprint beside each hash in `frame_hashes.json`, and assert the difference against a re-render is zero for the same build and small across builds. Two numbers, and the fallback becomes a check rather than a utility.

## 5 — Overlays are scheduled and still absent

**Severity: medium.**

v2.2 moved the Remotion overlay path into §21 as a phase-three feature with an acceptance test. That is honest scheduling and still no feature: titles are `drawtext`, and a designed lower-third is not expressible.

**Proposed resolution.** Keep it scheduled. The value of the change was that the document stopped implying the capability; the value of the next step is an owner and a date, which is a roadmap conversation rather than a specification one.

## 6 — The service and the worker do not share a store

**Severity: medium, and created by v2.2.**

`tests/service.py` uses an in-memory `JobStore`; `tests/store.py` uses SQLite. They implement the same states twice, so they can drift — and the HTTP layer, which is what a client sees, is not the layer that is durable.

That is exactly the defect this repository keeps finding: two implementations of one contract, each correct, never introduced to each other.

**Proposed resolution.** Make the service use `Store` and delete `JobStore`, so there is one state machine with one set of invariants and the HTTP tests exercise the durable path.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Finding 6 is the clearest example yet of the pattern this list has documented since v1.4: **the fix creates the next finding, and the next finding is always a second copy of something that should have one.**
