## 1 — The engine has never run as a service

**Severity: high, and it is the largest remaining gap.**

Everything in this repository is a library call. There is no API, no queue, no worker, no orchestrator, no idempotency store and no cancellation path — all of which §15, §17 and §18 specify in detail and none of which has ever executed.

That is a large gap and an honest one: the reference implementation proves the deterministic core, which is where the arithmetic lives and where a defect costs a frame. The runtime proves the contracts, which is where a defect costs a customer. Both need proving; only one is done.

**Proposed resolution.** A minimal service — one FastAPI process, one job table, one worker loop, no GPU — that implements create, poll, cancel and the `awaiting_input` hold against the real schema. It would test the state machine end to end and the idempotency key, and it needs no media at all.

## 2 — Frame hashes cover two hand-written graphs, not the fixtures

**Severity: high, verification debt.**

`test_render.py` renders two graphs written as string literals in the test. The eight golden fixtures in `tests/golden/` have never been executed, because they reference real assets that the repository does not carry.

So the renderer proves that *a* graph renders identically, not that *the compiler's* graph renders correctly. The distinction matters: a compiler bug that emits a plausible but wrong graph would pass the goldens (they would change together) and pass the render test (different graph).

**Proposed resolution.** Generate synthetic assets for the fixtures — `testsrc2` for picture, `sine` for audio — with the durations the IRs assume, so Appendix A and the audio mix can be compiled *and* rendered. Then the golden graph and the golden hash describe the same artefact.

## 3 — The repair loop is specified and not implemented

**Severity: high, verification debt.**

§7.4 specifies a loop: preview, run checks, feed a structured diff back to the planner, up to two attempts, under a call and deadline budget. `planner.validate` implements the checks and nothing implements the loop — so the budget behaviour, the attempt ceiling and the "fail with a specific reason" rule are untested.

**Proposed resolution.** Implement the loop against the template planner with a deliberately bad first plan, and assert three things: it repairs within two attempts, it fails with a named budget when the ceiling is hit, and it never loops forever.

## 4 — Identity accuracy targets are unmeasured

**Severity: medium, verification debt.**

§8.6 sets false-positive ≤ 1%, false-negative ≤ 2% and a grey band ≤ 8% of detections. No labelled set exists, so those are targets in the sense §2.2 defines — unvalidated — and the section says so.

**Proposed resolution.** Not urgent, because the feature is off by default and gated on legal review. When it is picked up, the set must span lighting, angle, occlusion and age, and the numbers must be reported at the configured operating point rather than as a curve.

## 5 — The Remotion overlay path is `drawtext`

**Severity: medium, and it is a defect rather than debt.**

§11.7 specifies Remotion rendering into an alpha-capable intermediate, composited at the correct record frames, so a graphics failure degrades to "no titles" rather than "no video". The compiler emits `drawtext`, which is a different product: no motion graphics, no designed titles, no alpha compositing.

**Proposed resolution.** Either implement the Remotion path or narrow §11.7 to what is built. A specification that describes a feature the reference implementation does not have is the failure mode §6.4 names — an enum value is a promise — applied to prose.

## 6 — Per-shot colour matching has no acceptance test yet

**Severity: low.**

v2.0 moved per-shot matching from "unimplemented compiler step" to "analysis feature in the roadmap", which is the right place for it. It still needs the acceptance test that makes it a feature rather than an aspiration: two shots of the same scene under different exposure, matched within a stated tolerance.

**Proposed resolution.** Define the tolerance — a ΔE threshold on a set of matched frames — before the feature is scheduled, because a feature whose success is undefined cannot be estimated.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Two of the six above are consequences of v2.0's own work: the renderer proves a graph rather than the compiler's graph, and the planner exists without the loop that drives it. That ratio has held since v1.4 and is now the most predictable thing in this repository.
