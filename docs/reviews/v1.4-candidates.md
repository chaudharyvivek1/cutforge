# v1.4 candidates — open findings against v1.3

Ten findings that v1.3 does not resolve. They are recorded here rather than in the specification for one reason: **the specification should not claim more than it has earned.** A finding that has been noticed but not designed is not a section; it is a debt, and debts belong in a list where they can be counted.

Each entry states the section it touches, what is wrong, the arithmetic that shows it, why it matters, and a proposed resolution. Where a proposal would change the IR or the tool surface, that is said explicitly, because those are the changes that need a version bump rather than an edit.

## 1 — There is no conform map

**Severity: critical. This is the one that will produce a wrong render.**

§5.3 says ingest conforms every asset to the project rate and that "the filter graph never performs rate conversion". §5.6 then computes how much source a clip consumes, and its answer is in **native** frames. Nothing converts one to the other.

For same-rate media the two domains coincide and the omission is invisible — which is why three reviews passed it. For mixed-rate media they diverge by the rate ratio.

```text
Record duration            R = 300 frames at 30000/1001  = 10.010 s
Source rate                fps_src = 25
Native consumption         S = R x fps_src / fps_proj = 250.25 -> 250 native frames
Conformed consumption      C = R                     = 300 conformed frames
```

The compiler decodes the conformed derivative, so it needs **300**, and §5.6 hands it **250**. A compiler that follows the document renders 50 frames — 1.7 seconds — short, and every downstream check agrees with it, because the IR was validated in native space too.

The naive repair is worse than the omission. Conforming the §5.6 answer double-rounds:

```text
2x speed, 300 record frames, 25 fps source:
  S_native = 300 x 2 x 25 / (30000/1001) = 500.5 -> 501
  501 native conformed = 501 x 30000 / (1001 x 25) = 600.6 -> 601
  correct answer = R x s = 600
```

One frame wrong, from one extra rounding — the same class of error v1.0 had, reintroduced a layer down.

**Why it matters.** Every mixed-rate project is affected, and mixed-rate is the normal case: a phone at 29.97, a camera at 25, a drone at 23.976, a screen recording at VFR. The failure is silent because the output is a valid video of the wrong length.

**Proposed resolution.** A `ConformMap` artefact per asset, produced at ingest, stored beside the derivative, named by a version on the asset row. Affine implementation for constant rate, table implementation for VFR, one interface. The compiler resolves every clip through it once and never sees a native frame. Speed is then computed in conformed space as `C = R × s`, rounded once, and §5.6's native figure is demoted to a reporting value used for bounds checks against the original.

Two invariants follow and should be added to §6.5: the conformed image of a source range must lie within the conformed asset duration, and the conform map version must be named by every clip's asset, so a re-conform cannot silently reinterpret an existing timeline.

## 2 — Speed says nothing about audio

**Severity: high.**

`speed` is a rational on the clip. It changes picture duration and is silent on sound, so three different products are expressible by the same IR: pitch preserved, pitch shifted, and muted. A compiler must guess, and a guess that differs from the planner's intent produces a chipmunk take or a silent clip that no schema check catches.

**Proposed resolution.** `speed` becomes an object: `{num, den, audio: "atempo" | "resample" | "mute"}`, required when speed ≠ 1 and forbidden when speed = 1. `atempo` is the default. Because ffmpeg restricts atempo to 0.5–2.0, factors outside that range compile to a cascade generated from the exact rational (`4x` → `atempo=2.0,atempo=2.0`), with the residual tracked so the last stage is not rounded from an already-rounded product. The audio invariant is asserted, not assumed: source samples consumed equal `samplesFor(C)` and record samples emitted equal `samplesFor(R)`.

## 3 — Captions and markers are never remapped

**Severity: high.**

Word timings arrive from ASR in source time. §11.4 specifies caption rasterisation in detail — resolution, fonts, safe areas — and never says how a word's timestamp becomes a record frame. When a clip is trimmed, sped up or reordered, the cue must move by exactly the amount the clip moved, and nothing in the document says so.

**Proposed resolution.** One affine source-to-record transform per clip, derived from the conform map and the speed, used by clips, captions, markers, chapter points and ducking envelopes alike. Caption cues are stored in **record** time in the IR, not source time. A cue spanning a cut is split into one cue per clip. The acceptance test is a property rather than a fixture: for every word in a transcript, the computed record frame equals the frame at which the caption becomes visible, within one frame.

## 4 — Capacity and cost price the same GPU differently

**Severity: high. This one is visible in the unit economics.**

§12.3 derives **2.77** concurrent realtime 4K60 streams per L4. §12.4 sizes a fleet at `ceil(concurrent / 2.77)`. §20 then prices a 4K60 output minute at **1.5× realtime**, which is 40 GPU-seconds per output minute.

Those cannot both be the planning basis. At 2.77 streams per card, a card-minute produces 2.77 output minutes, which is **21.7** GPU-seconds each, not 40. The 1.5× figure describes one job owning a whole card at 36% utilisation.

```text
P = $0.50/GPU-hour
dedicated  (1.5x realtime, 1 job/card)   40.0 GPU-s/output-min   $0.00556
headroom   (2.0 streams, 30 s/min)       30.0 GPU-s/output-min   $0.00417
packed     (2.77 streams, 21.7 s/min)    21.7 GPU-s/output-min   $0.00301
                                                 dedicated/packed = 1.85x
```

**Why it matters.** A business case built on $0.00556 per output minute over-states 4K60 render cost by 85% against a fleet that is actually packed, and a fleet planned at 2.77 streams while costing at 1.5× is internally inconsistent — the number that appears in the deck is not the number the scheduler produces.

**Proposed resolution.** Name the three operating points in §12.11, with the GPU-seconds and dollars for each, and state which one planning uses. Recommend the headroom point at 2.0 streams: packing to 2.77 saturates the encoder, leaving no slack for the p95 job, and the encoder is already the binding constraint. Then §20 quotes $0.00417 and the table gains a line saying why it is not the dedicated figure.

## 5 — Erasure does not propagate

**Severity: high, and legal before it is technical.**

§16.3 says deleting an asset deletes derived biometric artefacts in the same transaction. Three things survive that: analysis artefacts in the content-addressed cache, already-delivered renders containing the person, and the vector index entries that make them findable.

A deletion request that removes a row and leaves a searchable embedding and a delivered MP4 has not been honoured. Under India's DPDP Act, 2023 the obligation attaches to the processing, not to the row.

**Proposed resolution.** An erasure record per (tenant, asset or person) that drives four actions with a stated deadline: cache keys invalidated, index entries removed, dependent renders marked `quarantined` rather than deleted, and an entry written to an append-only erasure log. Whether a delivered render is deleted, withdrawn or retained as a lawful record is **a legal decision, not an engineering one** — the engine's job is to make every affected artefact findable and to apply whichever policy counsel sets. §16.6 should say so in those words.

## 6 — "Every op has an inverse" is false for three ops

**Severity: medium.**

§6.6 states that every op has an inverse and that undo is therefore free. Three ops make that untrue as written.

`remove_clip` carries a clip id and nothing else, so its inverse needs the clip's full definition — which the op does not contain. `trim` carries the new range and not the old one. `snap_to_beat` recomputes from an audio analysis and has no value inverse at all.

**Proposed resolution.** Restate the claim as: **an inverse is a function of (base revision, op)**, materialised at apply time and stored in the revision record, so undo is a read rather than a re-derivation. `snap_to_beat` is expanded by the planner into concrete move and reorder ops before it reaches `apply_ops`, and the tool rejects one that arrives unexpanded with `SNAP_NOT_EXPANDED`. The cost is one extra JSON array per revision; the benefit is that undo is correct by construction rather than by re-derivation against code that may have changed.

## 7 — Tolerances are expressed in frames

**Severity: medium.**

`tolerance_frames` appears in the Edit Plan and in the beat-snapping rules. Four frames is 133 ms at 29.97 and 67 ms at 59.94, so the same plan tolerates twice the sloppiness in a 30 fps project.

```text
120 ms  ->  4 frames at 30000/1001
        ->  7 frames at 60000/1001
```

**Proposed resolution.** Author every tolerance in milliseconds or beats; convert to frames once at compile time. This applies to the beat tolerance, the duration target (§7.2) and the transition handle check (§5.7). A tolerance that rounds to zero frames is rejected, because it is an exact requirement expressed as an approximate one.

## 8 — A held job has no column to store its deadline

**Severity: medium.**

§15.4 says `GET` on an `awaiting_input` job returns a question payload and **a deadline**. `jobs` has no column for one, so the deadline is either invented at read time from `started_at` plus a constant, or not reported at all. A contract the schema cannot satisfy is a contract that will be implemented three different ways in three clients.

**Proposed resolution.** Add `hold_deadline timestamptz` and `hold_question jsonb` to `jobs`, both nullable and both required non-null when `state = 'awaiting_input'`, enforced by a `CHECK` constraint. The orchestrator's sweeper fails any held job past its deadline, which makes the "timeout is not consent" rule a database fact rather than a worker behaviour.

## 9 — `speed_curve` is in the effect enum but not in the compiler

**Severity: low, but it is the general case of a real problem.**

§6.4's effect union includes `speed_curve` while §2.3 lists speed ramps as a non-goal. A planner reading the schema will use it, because the schema is the contract, and the compiler will reject it — or worse, ignore it and render a constant speed while the plan claims a ramp.

**Proposed resolution.** Remove it. Then adopt the rule this establishes: **an enum value is a promise the compiler keeps.** Adding a value to the effect union requires a compiler implementation, a fixture and a test in the same change, and a CI check should assert that the enum in the schema and the dispatch table in the compiler contain the same set.

## 10 — Assets carry no upstream provenance

**Severity: medium, and it grows as the platform grows.**

In a single-engine system, every asset came from an upload. In a platform with a 3D engine, a dubbing engine and a character platform, most assets come from another engine — and nothing in the IR records which one, or which job.

The consequence is diagnostic rather than cosmetic: a video that looks wrong because a sting was rendered with the wrong camera is indistinguishable from a video that was cut badly, and the render manifest cannot say which.

**Proposed resolution.** Add `origin: {engine, job_id, version, params_hash}` to the asset manifest and record it in the render manifest (§11.6). Additive, no behaviour change, and it makes the manifest a provenance record rather than a recipe. `docs/engine/02-engine-contract.md` §8 carries the proposed shape.

## How this list is maintained

A finding enters this list when it is **noticed and substantiated** — a section number, an arithmetic error, or two sections that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Two conventions keep the list honest:

- Every finding cites a section, not a feeling. "The time model is fragile" is not a finding; "§5.6's answer is in a domain the compiler does not decode" is.
- Every arithmetic claim is checked by `build/check_figures.py`. The double-rounding case, the three operating points and the tolerance conversion are all asserted there, so a future edit that changes a number has to change the check as well.
