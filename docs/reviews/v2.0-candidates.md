# v2.0 candidates — open findings against v1.9

All six findings from the previous list are resolved in v1.9. What follows is what v1.9 leaves open, and the shape of the list has changed: the remaining gaps are no longer between the document and its tooling, they are between the document and a working system.

| 1 | No pixels are ever produced | §19 | High | Verification debt |
| 2 | Working-space colour and per-shot matching are not compiled | §11.4 | High | Verification debt |

Every one of the six is verification debt. That is the first time the list has contained nothing else, and it is worth saying plainly: the document no longer has a known contradiction in it. What it has is an implementation that stops at the filter graph.

## 1 — No pixels are ever produced

**Severity: high, and it is the deepest gap in the repository.**

Every check proves a string. The compiler emits a filter graph, the goldens compare it byte for byte, and nothing runs ffmpeg. §19's first compiler gate — "golden frame hashes match for every fixture" — does not exist and cannot exist until a renderer runs in CI.

The consequence is precise: the graph could be syntactically perfect and semantically wrong in a way no string comparison sees. A `trim` with the wrong end frame compiles cleanly. A tone-map chain with the stages in the wrong order compiles cleanly. A `xfade` whose offset is a quarter-second off compiles cleanly.

**Proposed resolution.** Render the golden fixtures with ffmpeg in CI and compare frame hashes for the deterministic paths. Start with the two that need no colour management: Appendix A and the audio mix. A 45-second 1080p render is a few seconds on a CPU runner, which is affordable for four fixtures and would turn the compiler's guarantees from syntactic into semantic.

## 2 — Working-space colour and per-shot matching are not compiled

**Severity: high, verification debt.**

§11.4 specifies three colour steps: normalise to a working space at ingest, match shots, apply a creative LUT. v1.9 compiles the third. The first two are named as unimplemented and the compiler raises rather than skipping, which is the right failure mode and still a hole: an IR needing per-shot matching cannot be built.

**Proposed resolution.** Working-space conversion is a `zscale` chain and a manifest entry; per-shot matching needs a measurement pass over the conformed proxies and a gain/offset per clip, which is analysis work rather than compiler work. Split the finding: compile the first in v2.0, and move the second into the roadmap as an analysis feature with its own acceptance test.

## 3 — The planner and repair loop have no reference implementation

**Severity: high, verification debt.**

§7 specifies two planning passes, a plan DSL, grounding rules, a repair loop with budgets and a duration ladder. `spec_rules.duration_band` implements the ladder's four bands and nothing else. There is no reference planner, no reference repair loop, and therefore no test of the rule that matters most commercially: that a model's output lands on frames.

The 80%-first-attempt target in §2.2 cannot be measured against anything in this repository.

**Proposed resolution.** A deterministic reference planner — the §7.6 template planner that P0 ships before any model — plus a fixture set of ten structured requests and their expected plans. That tests the DSL, the grounding rules and the ladder without needing a language model, and it is the same component the roadmap already requires.

## 4 — The identity path has no reference implementation

**Severity: medium, verification debt.**

§8 specifies enrolment, matching, a grey band, a blocking hold and accuracy targets. None of it is implemented or tested here, and the accuracy targets are the kind of claim that should not be made without a labelled set.

**Proposed resolution.** Not a v2.0 priority, because the feature is off by default and gated on legal review. What *is* worth doing early: a test for the state machine — uncertain routes to hold, a hold expires to failed, an unanswered job never delivers — which needs no biometrics at all.

## 5 — OTIO export and Remotion overlays are specified and not compiled

**Severity: medium, verification debt.**

§11.7 specifies an alpha-capable overlay path and OTIO export with effects flattened where no NLE equivalent exists. The reference compiler emits `drawtext` for titles and nothing for overlays or export.

**Proposed resolution.** OTIO export is a translation of the IR and is testable without a renderer: emit the document, re-read it, assert the timeline round-trips. That is a cheap and high-value test. The Remotion path needs a browser and belongs with finding 1.

## 6 — The layout check runs on main only

**Severity: low.**

The layout job costs about two minutes because it installs LibreOffice, so it is gated to pushes to `main`. A pull request that breaks the layout passes CI and fails after merge.

**Proposed resolution.** Cache the LibreOffice install, or move the layout tests to a container image built once a week. Neither is hard; both are more work than the finding deserves until someone is actually opening pull requests.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

The character of the list has changed three times. Through v1.5 it held contradictions: two rules that could not both hold. v1.6 and v1.7 held defects in code the document had just added. v1.8 held defects in the artefact. v1.9 holds none of those — it holds the distance to a working renderer. That progression is the most useful thing in this file.
