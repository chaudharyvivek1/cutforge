## 1 — No scheduler: one worker, no concurrency, no fairness

**Severity: high.**

`tests/store.py` gives one worker a claim on one job. §17 describes a queue with depth and oldest-job-age alerts, and §12.4 sizes a fleet of GPUs; none of that is exercised. A single-worker reference cannot show starvation, cannot show a tenant monopolising the queue, and cannot show the p95 latency that §12.9's benchmark matrix measures.

**Proposed resolution.** N workers against one store, with a fairness rule across tenants and a test that one tenant submitting fifty jobs does not starve another submitting one. That is the smallest scheduler worth the name, and it is testable without a GPU.

## 2 — The retry policy has no backoff and no jitter

**Severity: medium, and it is the defect that turns a retry into a thundering herd.**

`Store.fail()` requeues a transient failure immediately. Every worker that failed at the same moment retries at the same moment, which is how a recovering dependency is knocked over again. §18 says backoff with jitter and does not implement it here.

**Proposed resolution.** A `retry_after` column and a claim that ignores jobs before it, with exponential backoff and a jitter seeded per job so two jobs do not align.

## 3 — `quarantined` is missing from the job state CHECK

**Severity: high, and it is the schema drifting from the code — the exact defect class this repository has documented since v1.3.**

v2.3 added a `quarantined` state to the store. §13.3's `jobs.state` CHECK still lists the six states it had in v1.3. A real Postgres deployment would reject the update the store now performs, and the migration checker does not compare states against code.

**Proposed resolution.** Add `quarantined` to the CHECK, and extend `build/check_sql.py` to compare the state list in the DDL against the `TERMINAL` tuple and the retry policy in `tests/store.py`. Two lists, one contract.

## 4 — The acrossfade fixture asserts length and not content

**Severity: medium, verification debt.**

The v2.3 test proves the decoded sample count is right — which is what §11.5 asks — and says nothing about whether the crossfade is in the right place. A fade applied at the wrong offset would produce the same length.

**Proposed resolution.** A golden hash on the decoded audio for the acrossfade fixture, so both the length and the content are pinned. Cheap, and it would catch an offset bug that a length assertion cannot.

## 5 — Overlays remain scheduled and unbuilt

**Severity: medium, and unchanged for two versions.**

The specification is honest about it and the feature does not exist. That is the right state for a document and a poor one for a product: a designed lower-third is not expressible in `drawtext`.

**Proposed resolution.** Either build the Remotion path or remove it from §11.7 and §21 and state that v1 has text-only overlays. Two versions of "scheduled" is one version too many for a document that prides itself on naming its gaps.

## 6 — The synthetic corpus could be mistaken for a measurement

**Severity: low.**

`golden/corpus_fixture.json` opens with a note saying it is synthetic, and a reader who skims will miss it — then quote an accuracy figure derived from two Gaussian clusters.

**Proposed resolution.** Rename the file to make the claim impossible to misread — `corpus_fixture_synthetic_not_a_measurement.json` — or have the loader refuse to compute rates unless the caller passes `synthetic=True`. The second is better: it puts the warning in the type system rather than in a comment.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Finding 3 is the pattern in its purest form yet: the code gained a state and the schema did not, which is exactly what §0 of v1.3 accused v1.2 of. Six versions later the same defect appeared in the version that added a quarantine.
