## 1 — Tokens never expire, rotate or revoke

**Severity: high, and it is the same class as v2.4's header defect: a stub that looks like an implementation.**

`auth.Tokens` is a dictionary. A token lives until the process ends, cannot be revoked without a restart, and carries no expiry. §16.2 requires short-lived access tokens, a refresh path, and revocation that takes effect on the next request.

The v2.5 fix moved the *decision* to the right place — the tenant comes from the credential — and left the credential itself unimplemented. That is progress and not completion.

**Proposed resolution.** An `expires_at` on `Principal`, a clock in `resolve()`, and a revocation set consulted on every request. Then a test that an expired token is 401 and a revoked one is 401 within one request, not one restart.

## 2 — No rate limiting or abuse controls

**Severity: high, verification debt.**

§16.1 specifies per-tenant quotas and a 429 with `Retry-After`. Nothing enforces a limit: a tenant can submit ten thousand jobs and the only back-pressure is the two-job concurrency cap, which delays rather than refuses.

**Proposed resolution.** A token bucket per tenant keyed on the same store, returning 429 with `Retry-After` when empty, and a test that the hundredth submission in a second is refused rather than queued. The concurrency cap is not a rate limit and should not be mistaken for one.

## 3 — Metrics cover the store and not the worker

**Severity: medium.**

Five signals are exported and all five come from the jobs table. §17's other four — GPU memory, encoder utilisation, heartbeat age and success rate by kind — are about a worker that does not exist in the reference. The table in §17 is honest about the split and the split is still a gap.

**Proposed resolution.** Emit `worker_heartbeat_age` from the reference worker, which already has a name and a clock. That is one gauge and it makes the alert rule testable.

## 4 — Webhook delivery has no loop, no retry, no dead-letter

**Severity: medium.**

`webhook.sign()` and `verify()` are tested; nothing delivers. There is no dispatcher, no retry with backoff, no dead-letter after exhaustion, and no ordering guarantee. §15.3 says delivery is at-least-once and receivers must be idempotent on event id — which is a promise the sender has to keep before the receiver can.

**Proposed resolution.** A dispatcher that reads terminal states from the store, signs and posts, retries with the same backoff policy §18 uses, and dead-letters after five attempts. Tested against a local receiver that fails twice and then accepts.

## 5 — The benchmark workflow has no runner

**Severity: medium, infrastructure rather than code.**

`build/benchmark.py` and the weekly workflow exist. No runner labelled `gpu` is registered, so the job queues and never runs, and §12.3's numbers remain targets.

**Proposed resolution.** Either attach a GPU runner or delete the workflow and say plainly that no throughput figure has been measured. A workflow that cannot run is the same failure mode as a test that skips — which this repository fixed in v1.8 and has now reproduced in CI.

## 6 — The identity corpus still has no data

**Severity: medium, and unchanged for three versions.**

`tests/corpus.py` is the specification of what to buy; the set does not exist. Nothing in the repository can change that.

**Proposed resolution.** Procurement. The contract is the useful artefact until then, and the harness refuses to report a number without it.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Three of the six above are consequences of v2.5's own work: a token store with no lifecycle, metrics with no worker to measure, and a webhook signer with no sender. The ratio has held since v1.4 and is now the most reliable property of this repository.
