## 1 — The compiler covers only Appendix A's operations

**Severity: high, and it is the honest limit of the golden layer.**

`tests/compiler.py` compiles cuts, gaps, speed, transitions and an audio bus. It does not compile overlays, colour management, captions, or the `xfade` alignment modes beyond centre. Appendix A uses none of those, so the golden file proves exactly what it exercises — and nothing more.

That is fine as a start and dangerous as a stopping point, because the untested operations are the ones with the most parameters. A `transform` with a rotation and a crop has more ways to be wrong than a trim.

**Proposed resolution.** Extend the fixture set one operation at a time, each with its own golden file: an overlay with an alpha channel, a tone-mapped HDR clip, burned-in captions at output resolution, and a wipe with `align: start`. Four goldens, four diffs, and the compiler's surface is covered in proportion to its risk.

## 2 — The extractor truncated code blocks for six versions

**Severity: high, tooling defect — and the most uncomfortable finding in this list.**

`build/extract_spec.py` ended a code block at the first blank line inside it, because a blank line is a paragraph containing one space and the blank-paragraph branch ran before the code test. Every listing with a blank line was silently cut at that point on extraction.

The figures survived because they live in prose and tables. The migration did not: the SQL check added in v1.7 found zero `CREATE TABLE` statements in the extracted document and thirty-three in the source. That is six versions of round-trip checks that were weaker than they appeared.

It is fixed in v1.7 — blank lines count as code when every run in the paragraph is monospaced — but nothing tests it, so it can regress silently again.

**Proposed resolution.** A round-trip test: build the document, extract it, and assert that the extracted markdown contains the same number of fenced blocks, the same number of `CREATE TABLE` statements and the same figure strings as the source. Cheap, and it would have caught this on the day it was introduced.

## 3 — The document build is not checked for determinism

**Severity: medium.**

§11.6 defines reproducibility as "same manifest, same bytes" for a render. The document's own build has no such guarantee: `build_docx.py` writes a `.docx` that contains timestamps and possibly unstable ids, so two builds of the same source are not byte-identical, and a reviewer cannot tell a content change from a packaging change.

**Proposed resolution.** Either normalise the package — strip `docProps/core.xml` timestamps and sort the zip entries — and assert byte-identity across two builds, or state plainly that the `.docx` is not byte-reproducible and the markdown is the artefact to diff. The second is one sentence and is the honest minimum.

## 4 — The 95th-percentile example uses one rate

**Severity: low.**

§20.3's commitment arithmetic multiplies 40 Mbps by thirty days and compares the result to a volume-based bill. It uses a single rate for the committed capacity and does not vary it, so it shows the shape without showing the decision.

**Proposed resolution.** Add the break-even: at what delivered volume does the commitment beat the two-tier volume price? One line of algebra and one number.

## 5 — `speedTerm` allows 16 but the cascade may not reach it

**Severity: low.**

§6.4's pattern admits 1–16 for both terms, so 16/1 and 1/16 are schema-valid. §5.11's cascade reaches 16 as `2.0 × 2.0 × 2.0 × 2.0`, which is four stages of atempo — legal, and the audio at that point is not intelligible. The schema permits something the document calls unusable.

**Proposed resolution.** Decide whether 16× is supported or merely bounded. If supported, say the cascade is four stages and that quality is the user's problem. If not, lower the pattern to 8 and say why. Right now the schema and the prose disagree about whether the value is usable.

## 6 — Nothing renders the document to check its layout

**Severity: medium, verification debt.**

Every check in this repository reads text. None of them looks at a page, and three real defects were found in the last two versions by rendering to PDF and reading it — the split table row, the nine-table build, the stale caption. Each was invisible to a text check until it had already shipped.

**Proposed resolution.** A layout smoke test: render to PDF, assert the page count is within a stated range, and assert that no page contains a line longer than the text column or a heading followed by nothing. It will not catch everything; it would have caught the nine-table build immediately.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Two of the six above are consequences of v1.7's own work: the compiler covers what the golden file exercises, and the SQL check found the extractor bug that had been hiding since v1.1. That is the same ratio again — roughly half of every list is created by the previous fix.
