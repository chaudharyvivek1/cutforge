# v2.2 candidates — open findings against v2.1

All six findings from the previous list are resolved in v2.1. What follows is what v2.1 leaves open.

## 1 — The service has no queue, no worker and no persistence

**Severity: high, and it is the honest limit of what v2.1 built.**

`tests/service.py` is one process, one dictionary and one thread. It proves the state machine is coherent — idempotency, the tenant-scoped 404, the hold, the terminal cancellation — and it proves nothing about a queue, a worker that dies mid-render, a retry that must not double-charge, or a restart that must not lose a job.

§18 specifies checkpointing at segment granularity and cooperative cancellation within thirty seconds. Neither has ever executed.

**Proposed resolution.** A worker loop against the same store, with a job that can be killed and resumed, and a test that kills it: the job must be recoverable, the idempotency key must still return one job, and a cancelled job must not resume.

## 2 — The render fixtures use one pattern per asset and no transitions on audio

**Severity: medium.**

`tests/assets.py` gives every asset a `testsrc2` or `smptebars` pattern at project rate. That is enough to catch a graph that cannot render and not enough to catch a graph that renders the wrong frames — two assets with the same pattern would hash identically if swapped, and the audio bus has no crossfade to test.

**Proposed resolution.** Give each asset a distinct pattern *and* a frame-number overlay, so a swapped input or an off-by-one trim changes the hash. Add an `acrossfade` fixture to exercise §5.7's audio handle rule against a real render.

## 3 — The repair loop is tested against a stub planner

**Severity: medium, verification debt.**

`test_repair.py` drives the loop with a planner that deliberately returns a broken plan. That proves the loop's control flow and says nothing about whether a real plan can be repaired — the template planner produces a correct plan first time, so the loop never runs on it.

**Proposed resolution.** A planner variant that under-delivers by a controllable amount, so the loop is exercised through the ladder's repair band rather than through a hand-broken structure.

## 4 — The Remotion overlay path is still not implemented

**Severity: medium, and now honestly labelled.**

v2.1 narrowed §11.7 to say what is built. That is the right fix for a misleading document and not a fix for the missing feature: designed titles, motion graphics and alpha compositing remain absent, and the compiler emits `drawtext`.

**Proposed resolution.** Either build it — a Remotion render to an alpha intermediate, composited at record frames, with a golden hash — or move overlays into the roadmap as a feature with an owner, so the specification stops implying a capability the engine does not have.

## 5 — Identity accuracy has a harness and no corpus

**Severity: medium, verification debt.**

`tests/accuracy.py` computes the rates correctly and a test proves it notices a bad threshold. The corpus it needs — labelled faces across lighting, angle, occlusion and age — does not exist and cannot be synthesised honestly.

**Proposed resolution.** This is procurement, not engineering: a labelled set has to be bought or built under consent, and §16.3's legal review gates it anyway. What can be done now is to fix the operating point and the reporting format, so the corpus has somewhere to land.

## 6 — The renderer pins one ffmpeg build and cannot say what changed

**Severity: low.**

A hash mismatch reports both ffmpeg builds and then skips. That is correct behaviour and a dead end: it cannot say whether the picture changed or the filter did. §11.6's manifest exists precisely to make that distinction possible.

**Proposed resolution.** When the build differs, re-render both sides and compare a downscaled perceptual metric rather than a hash — the same split §11.2 makes between identical decisions and non-identical pixels.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Two of the six above are consequences of v2.1's own work, which has held at roughly that ratio since v1.4. The pattern is stable enough to state as a rule: **every layer of checking makes the next layer's absence visible**, and the visible absence is always the one that was shipping.
