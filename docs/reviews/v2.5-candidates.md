# v2.5 candidates — open findings against v2.4

All six findings from the previous list are resolved in v2.4, along with seven defects found by a full audit of the code and the tests. What follows is what v2.4 leaves open.

## 1 — The service trusts a tenant header

**Severity: high, and it is the first security defect in the repository.**

`tests/service.py` reads `X-Tenant` and treats it as the tenant. That is a *reference* decision and it is also the shape of a real vulnerability: §14.5 says the tenant comes from the verified token, never from a header the client controls, and the test suite now demonstrates the wrong pattern convincingly enough to be copied.

The isolation tests are therefore testing isolation between two values the client chose. That is not nothing — the 404-not-403 behaviour is real — but it is not authorisation.

**Proposed resolution.** A `Principal` derived from a bearer token, with the tenant on it, and a test that a token for tenant A cannot read tenant B's job even when the header says B. The header becomes an override only an admin principal may send.

## 2 — No metrics, no tracing: §17's signals are never emitted

**Severity: high, verification debt.**

§17 specifies nine signals and their alert thresholds. The reference implementation emits none: no counters, no histograms, no `oldest_job_age`, no `worker_heartbeat_age`. The table is a promise nothing keeps.

That matters more than it looks, because three of the document's strongest claims — p95 preview latency, 80% first-attempt success, oldest-job-age — are only observable through those signals.

**Proposed resolution.** A `/metrics` endpoint in Prometheus text format, with the five counters the store can already produce (jobs by state, attempt histogram, queue depth, oldest job age, retry count). No dependency: the format is text.

## 3 — Webhooks are specified and not implemented

**Severity: medium, verification debt.**

§15.3 specifies signed webhooks with retry and a replay window. Nothing emits an event, so nothing can deliver one. The signature scheme has never been computed.

**Proposed resolution.** An event on terminal state, an HMAC over the body with a timestamp, and a test that verifies the signature and rejects a replayed timestamp. That is the whole of §15.3's risk and it needs no network.

## 4 — Every render in CI is CPU; NVENC has never run

**Severity: medium.**

The render tests use the pip-distributed ffmpeg on a CPU. §12.3's capacity model is built on NVENC session counts and NVDEC engines, and none of it has been measured. The document says so — every figure is marked a target — but the repository now gives the impression of having rendered 4K60, and it has rendered 320×180.

**Proposed resolution.** A benchmark job that runs on a GPU runner weekly and records the numbers into `docs/benchmarks/`, with the same "recorded beside the build that produced it" rule the frame hashes use. Until then, the README's technology table should say CPU only, which v2.4 does.

## 5 — The model path has no reference implementation

**Severity: medium, verification debt.**

§7.1 specifies two passes and a plan DSL; `tests/planner.py` implements the deterministic template planner that P0 ships *before* any model. The two-pass path, the grounding rules and the 80% first-attempt target have no implementation at all.

**Proposed resolution.** Not a correctness gap — the template planner is the P0 path and it is tested. What is missing is evidence for the model claim. A recorded plan corpus (prompt, model, plan, outcome) would make the target measurable without running a model in CI.

## 6 — The identity corpus still has no real data

**Severity: medium.**

Unchanged since v2.3 and blocked on procurement, not engineering. The harness, the contract and the synthetic fixture all work; the labelled set does not exist.

**Proposed resolution.** Buy or build one under consent. The contract in `tests/corpus.py` is the specification of what to buy, which is the useful thing this repository can produce before the data exists.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Two of the six above are consequences of v2.4's own work — a scheduler with no metrics to observe it, and a service whose auth was always a stub and is now load-bearing. The ratio has held since v1.4 and is the most predictable property of this repository.
