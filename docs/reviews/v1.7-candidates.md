## 1 — The conformance suite covers the rules, not the compiler or the planner

**Severity: high, and it is the honest limit of what v1.6 achieved.**

`tests/` proves the deterministic rules: conform maps, speed arithmetic, handles, beat grids, the duration ladder. It does not touch the two largest surfaces in the system — the compiler that turns an IR into a filter graph, and the planner that turns intent into ops.

Those are the components most likely to be wrong and least likely to be caught by a figure check. A compiler bug produces a valid file with the wrong content, which is the failure mode §17 says looks like success.

**Proposed resolution.** A golden-file layer: a fixed IR plus a fixed asset set, compiled to a filter graph, rendered, and compared by frame hash — with the graph itself committed as a golden file so a change to it is a reviewable diff rather than a silent behavioural change. This is P0 work in the roadmap and it belongs in the test plan before the compiler is written.

## 2 — The `jurisdiction` field is named and not specified

**Severity: medium, and created by v1.6.**

§16.6.1 says the erasure record carries a `jurisdiction` and the deadline is a function of it. It does not say what the field contains, where it is stored, what happens when it is absent, or which deadlines apply to which value. A field named in prose and absent from the schema is the defect §13.5 was written to catch — and the consistency checker does not catch this one, because it checks stored-versus-derived, not named-versus-specified.

**Proposed resolution.** Add `jurisdiction` to the erasure table with an ISO 3166-2 value, a lookup from jurisdiction to deadline that counsel owns as data rather than as code, and a stated default when the field is absent (the stricter of the configured values, never the looser).

## 3 — Nothing runs the tests automatically

**Severity: medium, verification debt.**

`tests/` exists and passes, and nothing invokes it. The three checks and the suite are run by hand, which means they run while someone remembers.

**Proposed resolution.** A workflow that runs `build/check_figures.py`, `build/check_consistency.py` and `python -m unittest discover -s tests` on every push, and fails the pull request on any of the three. The scripts already exit non-zero; the missing piece is one file.

## 4 — The VFR fixture never sits near the 1% threshold

**Severity: low, verification debt.**

`tests/vfr_fixture.py` generates a stream whose spread is 100% — a dropped frame doubles an interval. That proves the detector fires on obvious VFR and says nothing about the boundary. §5.4 sets the threshold at 1% of the nominal interval, and a file at 0.9% must be treated as constant rate while one at 1.1% must not.

**Proposed resolution.** A second fixture parameterised to sit either side of the threshold — 0.9% and 1.1% — asserting the classification flips. This is the kind of test that catches a threshold written with the wrong comparison operator, which is a bug that survives review indefinitely.

## 5 — `speed` bounds live only in the validator

**Severity: low.**

§5.11 requires both terms of the speed ratio to be at most 16, and §6.4's schema cannot express it because a rate is a string pair. So the bound is enforced after parse rather than at parse, and a caller learns about it from a validation error rather than from the schema.

**Proposed resolution.** Express the bound in the schema where it can be expressed — a `pattern` on the string that admits 1–16 — and keep the validator rule as the backstop. A schema that can say something should say it.

## 6 — The CDN commitment is mentioned and unpriced

**Severity: low.**

§20.3 says the effective egress rate is a function of peak behind a 95th-percentile commitment, and stops there. The two-tier arithmetic above it prices volume, not peak.

**Proposed resolution.** One worked example of a 95th-percentile bill: peak sustained rate × the commitment price, beside the volume-based figure for the same traffic, so the reader sees which of the two dominates for a spiky workload. Do not model it; show the shape.

## How this list is maintained

A finding enters when it is noticed and substantiated — a section number, an arithmetic error, or two rules that cannot both hold. It leaves when a version resolves it, and the resolution is named in that version's §0 table. It is never quietly dropped.

Three of the six above were created by v1.6's own work: the jurisdiction field by making deadlines configurable, the missing CI by adding something worth running, and the threshold gap by building a fixture that only exercises the obvious case. That ratio — half of every list created by the previous fix — is the strongest argument in this repository for keeping the list separate from the specification.
